# Spike S1 — execution, parsing and hints

**Date:** 31/08/2026 · **Gateway:** `ignition-module-testing` (192.168.153.128:8088), Ignition
**8.3.8**, Java 17.0.19, **Jython 2.7.4** (`jython-ia-2.7.4.0.jar`) · **Status:** complete, 5 of 6
answered empirically, 1 deferred.

Run without building a module. Jython can call Java directly, so the whole spike was a WebDev
`doGet` resource in a throwaway project (`_ScriptIDE_Spike_`, since deleted). Harness and raw
JSON responses are in [`S1-harness/`](S1-harness/).

## Verdict

**The plan survives, with one architectural change that is not optional.** Execution must NOT go
through `ScriptManager.runCode()` — it leaks one user's output into another's. The replacement is
proven and costs no capability.

| # | Question | Answer |
| --- | --- | --- |
| 1 | `addServlet("scriptide", …)` → `/system/scriptide`? | **Deferred** — needs a module. Copied pattern, low risk; verify in P0. |
| 2 | Per-thread stdout capture via `addStdOutStream`? | **NO — fails, and dangerously.** Fallback A+ works perfectly. |
| 3 | Does `interrupt(tid)` stop a runaway script? | **Yes at Python trace points; no when blocked in Java.** Works under `Py.runCode` too. |
| 4 | Does `ParserFacade` parse Python 2? | **Yes, all forms.** Errors are a plain `SyntaxError` with `lineno`/`offset`. |
| 5 | Does the project hints tree carry the project library? | **NO.** Identical to the gateway tree. |
| 6 | Structured traceback with clickable frames? | **Yes.** Library frames are `<module:name>`. |

## Q2 — output capture (the plan's #1 risk, and it materialised)

**The designed approach fails.** One `ThreadRoutingOutputStream` registered via
`sm.addStdOutStream()`, two concurrent `sm.runCode()` executions each printing 500 tagged lines:

| | lines received | own | **crosstalk** | lost |
| --- | --- | --- | --- | --- |
| Thread AAA | 477 | 455 | **22** | 45 |
| Thread BBB | 478 | 453 | **25** | 47 |

`unrouted_writes: 0` — the routing itself worked. The fault is upstream: Jython's `sys.stdout` is
a **single shared buffer**, so the thread that performs the `write()` is not the thread that
produced the bytes. This is the "far worse" outcome the plan named: **one user's output appearing
in another user's pane**, not mere loss.

### Fallback A+ — proven, and now the design

Give each execution its own `PySystemState`, bypassing `ScriptManager.runCode`:

```python
sm.runCode("pass", sm.createLocalsMap(), "<probe>")   # runCode leaves the manager's
mgr = Py.getSystemState()                             # state on THIS thread — no reflection

state = ScriptManager.createUtf8PySystemState(out, err)   # private stdout + stderr
state.modules = mgr.modules.copy()      # so `import system` / project libs resolve
state.modules.__setitem__("sys", state) # so explicit sys.stdout/stderr writes are private too
state.path = mgr.path
prev = Py.getSystemState()
try:
    Py.setSystemState(state)            # thread-local
    Py.runCode(Py.compile_flags(src, filename, CompileMode.exec, CompilerFlags()), locals, glob)
finally:
    Py.setSystemState(prev)
```

Measured with the same 2×500-line test: **0 crosstalk, 0 lost, 500/500 on both threads.**

Three sub-findings that each cost an iteration and must not be re-derived:

1. **A fresh `PySystemState` has an empty module registry** — `import system` and
   `import spikelib` both raise `ImportError`. Sharing `mgr.modules` fixes it.
2. **Sharing `mgr.modules` alone is not enough.** In Jython `sys.modules['sys']` *is* the
   `PySystemState`, so a shared map means a script's `sys.stdout`/`sys.stderr` are the
   **manager's**, not ours. `print` was isolated (it reads the thread-local state) but
   `sys.stderr.write(...)` was not. Fix: **copy** the map and point the copy's `sys` at our own
   state. Verified after the fix: `print` → private stdout, `sys.stdout.write` → private stdout,
   `sys.stderr.write` → private stderr, correctly split.
3. `getProjectScriptManager()` returns `ProjectScriptLifecycle$TrackingProjectScriptManager`, a
   distinct instance from `context.getScriptManager()`.

**Consequence for the plan:** delete `ThreadRoutingOutputStream` and the whole
`addStdOutStream` design. Fallback B (serialising executions gateway-wide) is not needed.

## Q3 — Stop

`ScriptManager.interrupt(tid)`, timed by the *caller* (the worker thread cannot time itself — see
below):

| script | interrupted at | total wall-clock | verdict |
| --- | --- | --- | --- |
| `while time.time() < end: pass` (would run 15 s) | 3.0 s | **3.0 s** | **stopped** |
| `time.sleep(10)` | 2.0 s | **10.06 s** | **not stopped** |

Both confirm the plan. Two implementation facts:

- **Interrupt still reaches a `Py.runCode` execution**, so bypassing `ScriptManager.runCode` for
  Q2 costs nothing here. This was the open risk in adopting Fallback A+.
- **The cancellation escapes Jython's exception machinery entirely.** Neither a bare `except:`
  nor `except java.lang.Throwable` in Jython caught it; the worker thread was killed outright
  before it could record its own elapsed time. In the module the user script is invoked from
  **Java**, so wrap `Py.runCode` in `try { … } catch (Throwable t)` — and note that a Jython-level
  `try/except` inside a *user's* script will not trap a Stop either, which is the behaviour we
  want.

The escalation ladder in the plan (interrupt → `Thread.interrupt()` → abandon) stands, as does the
honest "Stop is best-effort" UI copy.

## Q4 — Python 2 parsing

`ParserFacade.parseExpressionOrModule(new StringReader(src), filename, new CompilerFlags())`.
All eight Python-2-only forms parse to an `_ast.Module`:

`print "hello"` · `except ValueError, e:` · `10L` · `` `1` `` · `exec "x=1"` · `0777` · `1 <> 2` ·
`raise ValueError, "msg"`

`print("hello")` also parses. `f"{1}"` correctly **fails** — right behaviour for a Jython 2.7
target.

**Syntax errors are simpler than the plan assumed.** They surface as a plain Python
`SyntaxError` — *not* `org.python.antlr.ParseException` — carrying `lineno` and `offset`
directly:

```
'def f(:'        -> lineno 1, offset 6, "no viable alternative at input ':'"
'c = = 3' (L3)   -> lineno 3, offset 4, "no viable alternative at input '='"
```

So the plan's defensive "handle both exception shapes" is unnecessary; read `ev.lineno` /
`ev.offset`. Jython reports only the **first** error per parse, which matches the real Designer's
single red squiggle.

## Q5 — hints tree (a real negative)

`getProjectScriptManager(p).getHintsTree()` is **identical** to
`context.getScriptManager().getHintsTree()`: root `['system']`, 40 nodes, both. The project's own
library module `spikelib` is **absent**.

This is not a test artefact: Q6 imported and executed `spikelib` on that same ScriptManager, so
the library genuinely is loaded — it simply is not in the hints tree.

**Consequence:** platform completions come from the hints tree; **project-library completions must
come entirely from our own `ParserFacade` AST index**, which P4 builds anyway. A degradation, not
a blocker — exactly as the plan anticipated.

**The good news is the tree's quality.** `system.tag` yields 25 methods, each with description,
typed parameters (`name`, `optional`, `default`, per-parameter description) and a full
`TypeDescriptor` return type. That is everything completion, signature help and hover need, and it
confirms the premise the whole module rests on:

```
system.tag -> 25 methods: browse, browseHistoricalTags, configure, copy, deleteAnnotations,
              deleteTags, exists, exportTags, getConfiguration, importTags, move, query, …
restartProvider(provider)  param optional=false, desc 41 chars
              returns TypeDescriptor(name=bool, description="True if the provider was
              successfully restarted, False otherwise.")
```

## Q6 — traceback

Works, and the frame spelling is clean. Running `import spikelib; spikelib.level2()` under the
filename token `<script-ide:_ScriptIDE_Spike_:ignition/script-python/Spike/Console>`:

```
File "<script-ide:_ScriptIDE_Spike_:…/Console>", line 2, in <module>
File "<module:spikelib>",                        line 5, in level2
File "<module:spikelib>",                        line 2, in boom
ValueError: boom from library
```

- The custom filename token **round-trips verbatim** — the join key works.
- **Project library frames are spelled `<module:<dotted.module.name>>`** — parseable and
  reversible, so a frame inside a library function resolves to its resource and is clickable.
- Two extraction paths, use the right one per call style:
  `ScriptManager.runCode` → `JythonExecException.getPyCause()` → `PyException.traceback`;
  **`Py.runCode` (our path) → `sys.exc_info()[2]` directly**, walking `tb_frame.f_code.co_filename`
  / `co_name` / `tb_lineno` / `tb_next`. The plan's `getPyCause()` route does not apply to the
  execution path we are now using.

## Incidental findings (cost time; worth keeping)

- **The WebDev URL is `/system/webdev/<project>/<resource>`**, not `/data/<project>/<resource>` —
  the latter 404s. Verified against an unrelated known-good endpoint (`Demo-KPI/kpi_init`), which
  404s the same way.
- **`require-auth: true` with no user source on the project returns HTTP 500 "No user source for
  project."** — not 401, not 404. The existing `Demo-KPI/kpi_init` endpoint has been broken this
  way on this gateway. A 500 here means the resource **is** registered.
- **`logs/wrapper.log` is a symlink to `/dev/stdout`** on this container — `tail`/`grep` on it
  hangs forever. Use `docker logs --since <n>m`.
